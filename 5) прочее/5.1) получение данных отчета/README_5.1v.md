# 3.1. Получение данных отчета

## 1. Тип уязвимости

Тип уязвимости: получение данных отчета / нарушение ограничения доступа к данным / SQL-инъекция в фильтрации отчетов.

Пользователь смог управлять условием фильтрации SQL-отчета и получать данные, которые должны были быть ограничены условиями запроса и правами доступа. Вместо того чтобы разрешать только безопасный фильтр по текущему пользователю, сайт принимал введенный WHERE-фрагмент и использовал его при формировании отчета.

## 2. Результат уязвимости

В демонстрации пользователь `alice` с ролью `student` открывает страницу `SQL Reports` и меняет условие фильтрации отчета. При обычном условии `u.username = 'alice'` отчет не показывает данные, но после подстановки условий для других пользователей сайт возвращает чужие записи.

Например, при вводе `u.username = 'bob'` в отчете появляется строка клиента `Denis Morozov` с суммой `15250.00`, владельцем `Bob Manager` и подсказкой карты `7003`. При вводе `u.username = 'carol'` появляется запись `Natalia Volkova` с суммой `49999.00`, владельцем `Carol Admin` и подсказкой карты `9911`.

После проверки `1=1` сайт выводит сразу все доступные строки отчета, включая записи владельцев `Carol Admin`, `Alice Student` и `Bob Manager`. То есть пользователь смог получить данные отчета не только по корректному условию, но и за счет подмены условия SQL-запроса.

Использованные проверки/инъекции:

```sql
u.username = 'bob'
u.username = 'carol'
1=1
1=0
```

## 3. Как была найдена уязвимость

1. Открыла страницу пользовательских SQL-отчетов под учетной записью `alice`.
2. Проверила штатное условие `u.username = 'alice'`. В результате отчет не показал данных.
3. Изменила условие на `u.username = 'bob'` и запустила отчет. После этого отобразилась запись, принадлежащая пользователю `bob`.
4. Затем изменила условие на `u.username = 'carol'`. Отчет вернул данные, связанные с пользователем `carol`.
5. После этого ввела проверку `1=1`, которая делает условие всегда истинным. В результате отчет вывел все доступные записи.
6. Для обратной проверки ввела `1=0`. Так как это условие всегда ложное, отчет перестал показывать записи.

## 4. Причина уязвимости

Причина была в том, что пользовательский WHERE-фрагмент передавался в функцию отчета и использовался как часть SQL-логики. До исправления функция `runCustomReport(whereClause: string)` проверяла только то, что строка не пустая, а затем вызывала SQL-функцию с переданным пользователем условием.

Такой подход позволял пользователю менять фильтр отчета на произвольное условие, например `1=1`, и обходить ограничение по владельцу данных.

### Код до исправления

```typescript
export async function runCustomReport(whereClause: string) {
    if (!whereClause.trim()) {
        error(400, 'WHERE clause is required');
    }

    const result = await pool.query('SELECT * FROM training.run_custom_report($1)', [whereClause]);
    return result.rows;
}
```

Ключевая проблема здесь в том, что `$1` защищает только передачу значения в функцию, но сама функция дальше использовала этот текст как SQL-фрагмент `WHERE`. Поэтому строка `1=1` становилась не значением фильтра, а частью SQL-команды.

## 5. Исправление

После исправления свободный WHERE-фрагмент больше не используется. Сервер принимает только фильтр вида `u.username = '...'`, извлекает имя пользователя и передает его в параметризованный SQL-запрос как значение `$1`.

### Код после исправления

```typescript
export async function runCustomReport(whereClause: string) {
    const normalized = whereClause.trim();

    if (!normalized) {
        error(400, 'WHERE clause is required');
    }

    const usernameMatch = normalized.match(/^u\.username\s*=\s*'([^']+)'$/);

    if (!usernameMatch) {
        error(400, 'Only username filter is allowed');
    }

    const username = usernameMatch[1];

    const result = await pool.query(
        `
            SELECT
                c.full_name AS customer_name,
                i.amount,
                u.full_name AS owner_name,
                i.card_hint
            FROM training.invoices i
            JOIN training.customers c ON c.id = i.customer_id
            JOIN training.app_users u ON u.id = i.owner_user_id
            WHERE u.username = $1
            ORDER BY i.id
        `,
        [username]
    );

    return result.rows;
}
```

Теперь ввод пользователя не может превратиться в произвольное SQL-условие: строка `1=1` не проходит проверку формата, а имя пользователя используется как параметр запроса.

## 6. Вывод

Уязвимость позволяла получать чужие и полные данные отчета через подмену условия фильтрации. Для исправления нужно не принимать от пользователя произвольные SQL-фрагменты, а явно разрешать только нужные параметры фильтрации и передавать их в базу через параметризованные запросы.
